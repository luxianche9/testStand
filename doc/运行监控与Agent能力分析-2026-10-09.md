## 1. 运行监控为什么看起来乱，怎么收

### 1.1 现状：第一条曲线之前横向堆了 5 条控件带

| # | 控件带 | 来源 | 内容 |
|---|---|---|---|
| 1 | 台架标题行 | `features/bench/BenchPage.tsx`（475 行） | 运行监控/工位接线切换、保存状态、**时间跨度 + 跟随 + 复位时间轴**（`MonitorPane` portal 进来的 `tools`） |
| 2 | 运行头 | `features/testing/RunHeader.tsx`（90 行） | `RunSummary`（计划名、判定、进度、当前步骤、返回当前、跳到问题）+ `ExportButtons`（导出日志、导出 CSV）+ `RunControls`（暂停/继续/中止）+ 复核判定 + 返回实时 + `InlineWarning` |
| 3 | 事件时间轴 | `features/streams/RunOverview.tsx`（198 行） | 区域、步骤、判定、调用；自带一套 range |
| 4 | 示波器自己的工具行 | `features/streams/SignalScope.tsx:243`（464 行） | 「示波器」标题、● 实时、状态面板开关、分通道/叠加 |
| 5 | 下方面板 tab 行 | `features/monitor/MonitorPane.tsx:224`（268 行） | 控制台 / 报文 N——只有两个 tab，占满一整行 `h-8` |

再加上示波器里还有一条 `h-8` 的通道图例行（`SignalScope.tsx:197`）、右侧 `StatePanel`（178 行）和通道 `aside`，以及 3/4 之间的 `Splitter`。运行中的窗口上半部分几乎全是边框和小控件，留给波形的垂直空间被挤掉一半以上。

乱的根因不是单个组件做得差，而是**四个互不相识的组件各自贴了一条自己的工具带**：`BenchPage`、`RunHeader`、`SignalScope`、`MonitorPane` 都在往垂直方向加 `shrink-0 border-b` 的行，没人负责合并。

### 1.2 建议：5 条 → 2 条

1. **时间控件搬到示波器头上。** 时间跨度 / 跟随 / 复位现在通过 portal 放在**顶层标题行**，离它控制的时间轴和示波器隔着两条带。它们应该并进 `SignalScope.tsx:243` 那条行里（和 ● 实时、分通道/叠加同组），顶层标题行只留视图切换和保存状态。顺手去掉 `MonitorPane` 的 `toolbar` portal 依赖，少一条跨组件通道。
2. **`RunHeader` 按运行状态收起。** `RunControls`（暂停/继续/中止）只在 `live` 时有用，`ExportButtons` + 复核判定只在 `!live` 时有用，现在两组同框显示。改成「状态 + 一个主操作」常驻，导出 / 复核 / 返回实时进一个溢出菜单。`InlineWarning` 保持独立一行——它是真的需要被看到的。
3. **事件时间轴和示波器共用一条时间刻度。** `RunOverview` 和 `SignalScope` 各算一套 range，视觉上是两条无关的带。让时间轴贴着示波器顶边、共用刻度、去掉中间那条 `border-b`，两者合成一个「同一时间轴上的事件 + 波形」块。
4. **下方面板的 2-tab 行并进示波器工具行右侧。** 两个 tab 不值一整行；控制台/报文的切换可以和示波器的控件共处一行（右对齐），省掉整条 `h-8` 和一条边框。
5. 可选：`StatePanel` 和通道 `aside` 是两个并排的侧列，合成一个可折叠侧栏能再省一条竖边框。

做完 1–4 之后第一条曲线之前只剩：**顶层标题行**（视图切换 + 保存状态）和**一条合并后的仪表工具行**（时间跨度/跟随/复位 + 分通道/叠加 + 状态面板 + 控制台/报文），运行时额外一个「运行状态块」（运行头 + 共轴时间轴）。

## 2. AI Agent 能做哪些任务

数据来自操作注册表（`app/python/src/teststand_backend/application/__init__.py` 的 `OPERATIONS`）：**共 77 个 operation，其中 `profiles` 非空、即经 MCP 暴露给 Agent 的有 58 个**。注册表同时生成 HTTP 路由、MCP 工具和 TS 类型，所以这 58 个就是 Agent 能做的全部，没有旁路。

### 2.1 按 profile（一个 operation 可属多个）

| profile | 数量 | 用途 |
|---|---|---|
| `plan` | 31 | 编/校验测试计划、ICD、步骤目录 |
| `run` | 21 | 启动/暂停/继续/中止运行、等待、读日志与结果 |
| `adapter` | 14 | 设备清单、工具列表、定义、装设备包 |

### 2.3 风险分级与护栏（按实际代码，不是按印象）

暴露给 Agent 的 58 个里：`read` 39、`write` 12、`destructive` 2、`actuate` 5。

- **`confirm=True` 只有 5 个**：`devices.addDeviceFromFile`、`devices.removeDevice`、`devices.removeHardware`、`devices.saveDevice`、`testing.reconcileOperation`。
- **`actuate` 的 5 个**（`devices.callTool`、`testing.startRun` / `pauseRun` / `resumeRun` / `abortRun`）**都没有 `confirm`**。继电器、电压这类真正动硬件的写操作走的是 `devices.callTool`，它的护栏不是确认框，而是：
  1. `application/registry.py` 第 7 步——`actuate` 操作结果未知时直接失败为 `unknown_outcome`，**永不自动重发**（`registry.py:160` 判 `definition.spec.risk != "actuate"` 才允许重试）；
  2. `mcp_gateway/tool_registry.py:96` 把 `risk == "actuate"` 写进 MCP 工具注解，标成非只读；
  3. `mcp_gateway/agent-instructions.md` 里的硬约束：不绕过 testStand 直调厂商驱动；超时或结果未知的写操作先读回状态再决定。
- 也就是说「写类高风险操作都带 confirm」这个说法是**不成立的**。真实的设计是：**破坏性/不可逆的配置变更靠确认框，动硬件的操作靠「结果未知即失败、绝不自动重发」**。如果以后要给继电器/电压加确认，那是一个新决定，不是现状。

### 2.4 一条完整的链：照着手册做出一个新设备并装上

`skill/device-plugin` 的 9 步（读资料 → `new_device.py` 骨架 → `driver.py` → `sim.py` → `adapter.py` 的 `@tool` → 流和引脚 → `check_adapter.ps1` → `pack.py` → 人工实物验收）加上 `devices.addDeviceFromFile`（按绝对路径装 `.tsdev`，需人工确认），意味着 Agent 可以从厂商手册一路做到设备出现在设备列表里，只在**装包**和**实物验收**两处需要人。本次新加的「让 Agent 照着手册写新适配器」快捷按钮就是这条链的入口。

## 3. 「按文件添加硬件设备」这条路完不完整

| 包类型 | 人工入口 | Agent 入口 | 结论 |
|---|---|---|---|
| `.tsdev`（带驱动的设备包） | `+ → 添加设备…` → `pickDevicePackage()` → `dialogs.openDevicePackage()` → `devices.inspectPackage({data})` → `AddDeviceDialog`（设备 / 驱动版本 / 需要的厂商驱动 / SHA-256 / 名称输入 / 文件详情 / `restartRequired` 时提示重启） | `devices.addDeviceFromFile`（`confirm=True`） | **完整** |
| `.tshw`（被测件 / 夹具包） | 本次之前：导入只存在于 `editors/HardwareEditor.tsx:88` 的页脚，`+` 菜单够不到——想导入一个已有的包得先「添加被测件 / 夹具」开一个空编辑器 | 无 | 人工入口**本次已补**；Agent 入口仍缺 |

- 人工侧的缺口已修：`features/devices/BundleActions.tsx` 的导入路径抽成可独立调用的 `importBundleFile`，`+` 菜单直接调，`HardwareEditor` 复用同一份。
- 剩下一笔：`.tshw` 没有 `addDeviceFromFile` 的等价 operation，Agent 不能自己装被测件包。本次**没有加**（超出本次请求范围），记在这里备查。
