本文回答一个问题: 测试运行过程中, 实际的收发信息和采集数据看不到, 测试过程对人仍然是黑盒, 怎么解决。讨论从界面问题出发, 最终落到三层改动: 硬件服务的数据面、测试步骤的判定语义、运行页的重构。每个设计点标注实现状态, 约定与上位文档一致:

- ✅ 已实现: 代码中已有
- 🟡 部分实现: 机制存在, 但没有接入
- ⏳ 规划: 尚无代码

---

## 1. 问题与现状

### 1.1 问题

汇报材料把"测试软件内部是黑盒"列为定制测试软件的五个代价之一。当前软件在编排层解决了这一点: 流程是结构化数据, 每一步调用哪个硬件、哪个工具、参数是什么都能看到。但在**执行层**, 黑盒仍然存在:

- 一步串口测试执行完, 只能看到"调用了 `write_text`, 成功", 看不到实际发出的字节和设备的应答。
- 一步电压测量, 只能看到最终读数, 看不到激励之后电压如何建立、有没有稳定、有没有毛刺。
- 测试失败时, 无法回答"继电器闭合之后多久串口才有回应"这类时序问题。

### 1.2 现状: 数据已经有一半, 但没有接起来

| 层 | 现状 | 状态 |
|---|---|---|
| SDK 流 | `streams.py` 已有 `Stream` / `ByteStream` / `SampledStream`, 共用带 `seq`、`t`、`epoch` 的环形缓冲 (`ringbuffer.py`) | ✅ |
| SDK 数据通道 | `ws.py` 提供 `/streams/{streamId}?from=<cursor>` 只读 WebSocket, 有 `hello` / `batch` / `gap` / `status` 帧, 支持断线续传 | ✅ |
| SDK 工具 | `<prefix>_stream_read` / `_stream_start` / `_stream_stop`, `list_streams`, `get_panel` (含 `terminal` 控件) | ✅ |
| 适配器 | cp118u 串口收发进 `serial1..8` 字节流; pci1710l 有 `ai0..15` / `di` / `do` 采样流; pci1762 有 `di` / `relay`; pci6208v 有 `ao0..7` 软件影子流 | ✅ |
| 后端 | `engine.py` `invoke_device` 只记录参数哈希 (`inputHash`), 不记录参数、起止时间; 后端**从不**订阅任何设备流 | 🟡 |
| 桌面端 | 运行日志页有执行树、证据、原始事件列表; 没有时间轴、没有任何 TX/RX 或波形显示 | 🟡 |

结论: 缺的不是采集能力, 而是把设备流接到运行上下文里, 并让判定语义和界面能用上这些数据。

## 2. 目标与非目标

### 2.1 目标

1. 运行中和运行后, 人能看到每一步实际的收发字节和采集信号, 并且能对应到步骤。
2. 判定的证据是带时间戳的数据段, 不是一个孤立读数; 事后可以用录制数据复判。
3. 不削弱通用化前提: 适配器的必填契约不变大, 本地部署的模型仍能可靠完成硬件适配。
4. 数据模型能覆盖汇报材料承诺的资源范围: 模拟量、离散量、继电器、串口, 以及示波器、信号发生器等任意仪器。

### 2.2 非目标

- 不做通用示波器软件; 显示能力以测试排障为限。
- 不引入 MQTT / NATS 等消息中间件 (见 D19)。
- 不改变现有 MCP 工具的名字、参数和返回结构; 已有方案、Agent 提示词、测试计划继续可用。
- 运行中不提供手动发送; 手动调试仍在手动页完成。

## 3. 关键设计决策

| 编号 | 决策 | 理由 |
|---|---|---|
| D17 | 控制面和数据面分离: 控制走 MCP, 数据走带游标的流通道 | MCP 是通用化的核心卖点, 请求/响应适合"调用一个工具"; 但高频数据用 MCP 资源订阅要"通知后再拉", 来回太多。模型也不需要原始波形, 给它摘要即可 |
| D18 | 所有数据源统一为"带时间戳的日志 + 游标" | 运行事件 (`readRunLog`) 和设备流 (`?from=cursor`) 本来就是这个模型。统一后, 实时 = 从游标回放并跟到最新, 实时监控和事后回放共用一套代码 |
| D19 | 现阶段不上消息中间件, 由后端 `StreamHub` 汇聚 | 每台工控机多部署一个服务代价高; 硬件同一时刻只被一个终端占用, 没有多终端围观需求。以后有需求时只替换 `StreamHub` 的上游 |
| D20 | 数据不走现有 stdio 控制通道 | 中止命令也走这条通道; 波形数据把它占满就是安全问题。数据走后端单独的本地 WebSocket |
| D21 | 语义放 SDK, 原语放适配器, AI 只写原语 | 连续采集、时间戳、窗口统计、等待条件、事务、对时这些是本地模型最不擅长的并发与时序工作, 且各厂商 SDK 差异最大。做进 SDK 一次写对, 适配器只写 `sample()` 和读写函数 |
| D22 | 适配器契约分层 (T0 必填, T1–T3 可选), 缺层时 SDK 降级并如实声明分辩率 | 每块新板卡至少能进台架 (T0), 能力随资料和人力逐步补齐; 不因为一层做不到就整卡不可用 |
| D23 | 判定按设备时间戳查时间窗口, 不用终端手里的"最新值" | 终端收到的值滞后一个采样周期加网络加攒批; 上一轮残留值会让新激励未生效的步骤误判通过; 丢帧断线时必须判"证据缺失"而不是沿用旧值 |
| D24 | 连续采集只用于原始信号板卡, 智能仪器保留自带测量 | SCPI 仪器一次查询几十毫秒, 有自己的触发和采集逻辑, 强迫它按连续流工作反而不通用。通用语义是"带时间戳的证据", 不是"连续采样" |
| D25 | 运行中仪器面板只读 | 人和测试脚本同时操作同一设备会互相干扰; 手动发送留在手动页, 复用同一套仪器组件 |
| D26 | 时间戳由 SDK 打, 时钟偏移由后端估算, 适配器不碰时钟 | 对时是跨设备判定正确的前提, 但不能成为每块卡的义务 |

## 4. 总体架构

### 4.1 控制面与数据面

```
                控制面: MCP 请求/响应 (保持通用)
 测试引擎 / AI Agent / 手动面板 ─── tools/call(_meta.operationId) ───►  设备服务 (SDK + 适配器)
                                                                            │  带时间戳的环形缓冲
                数据面: 流日志 (按游标订阅、断线续传)                          │
 设备服务 ── WS /streams/{id}?from=cursor ──► 后端 StreamHub ──┬─► RunStreamRecorder → runs/<runId>/streams/*.jsonl
                                                               ├─► 本地数据 WS ──► 渲染进程: 示波器 / 终端 / 时间轴
                                                               └─► Agent 查询工具 (按步骤给解码帧和统计, 不给原始数据)
```

- 一路设备流在 `StreamHub` 里只连一次上游, 录制、界面、Agent 三方共享。
- 同一份环形缓冲同时服务 MCP 工具 (`stream_read`、`measure`、`wait_until`) 和 WS 订阅, 三种读法看到的是同一序列号 (现状即如此, 见 `streams.py` 模块文档)。
- 后端通过 WS 订阅本身就构成"有人在看", `SampledStream` 会持续采样, 运行期间**不需要**再调 `stream_start`。`stream_start` 留给 AI 和手动调试。

### 4.2 三个必须解决的技术点

| 技术点 | 做法 |
|---|---|
| 帧与步骤关联 | 引擎调用工具时通过 MCP `_meta` 传 `operationId` (`mcp_client.call_tool` 已有 `meta` 参数)。SDK `manager.invoke` 放进 contextvar, `RingBuffer.append` 自动给每条数据带上 `op`。工具返回时附 `_meta.streamRefs: [{streamId, fromSeq, toSeq}]`, 步骤证据精确指向数据段 |
| 时钟对齐 | WS `hello` 帧和 ping 回包加 `serverTime`; `StreamHub` 估算每台设备服务的时钟偏移 (局域网约 1 ms 级), 统一换算为后端时间 |
| 时序精度 | 单设备的时序条件在设备端算 (`measure` / `wait_until` / `transact`), 激励与采样用同一块卡的时钟; 跨设备条件在后端算, 窗口起点取保守值 (见 7.3) |

## 5. 数据模型

### 5.1 流的类型

在现有 `push` / `bytes` / `sampled` 之上, 按**数据形状**重新归类, 补三种类型。所有类型的每条记录都带 `seq`、`t`、可选 `op`。

| shape | 每条记录 | 典型资源 | 界面 | 现状 |
|---|---|---|---|---|
| `scalar` | `{value}` | AI 电压、温度、DMM 读数、AO 设定值 | 示波器折线 | ✅ `Stream` / `SampledStream` |
| `bitmap` | `{value: int, meta.bits}` | DI、DO/继电器回读 | 示波器阶梯, 按位展开 | ✅ |
| `vector` | `{value: {ch: number}}` | 多通道同步扫描 | 示波器多通道, 时间对齐 | ⏳ |
| `bytes` | `{dir, bytes, hex, text}` | 串口、TCP 透传 | 终端 HEX/ASCII | ✅ `ByteStream` |
| `frame` | `{dir, id, payload, flags}` | CAN、LIN、SPI 事务 | 终端按帧显示, 按 id 过滤 | ⏳ `FrameStream` |
| `block` | `{t0, dt, samples[]}` | 示波器波形、硬件定时采集 | 示波器, 拼接时间轴 | ⏳ `BlockSource` (T2) |
| `blob` | `{ref, mime, bytes, sha256}` | 示波器截图、摄像头、日志文件 | 证据附件, 按 `ref` 取回 | ⏳ |
| `mark` | `{kind, detail}` | 配置串口 9600 8N1、清空 RX、量程切换 | 终端分隔线 / 波形标记 | ⏳ `stream.mark()` |

### 5.2 流描述字段

`describe()` 现有 `streamId`、`kind`、`label`、`unit`、`valueSchema`、`requires`、`state`、`epoch`、`head`、`tail`、`channel`、`meta`。新增:

| 字段 | 取值 | 用途 |
|---|---|---|
| `shape` | 5.1 中的类型 | 界面自动选用终端或示波器 |
| `source` | `measured` / `readback` / `shadow` | 实测画实线, 回读和软件影子画虚线; 与工具的 `evidenceType` 一致 |
| `range` | `[min, max]` | 示波器纵轴 |
| `timeResolutionMs` | 数值 | 软件轮询的真实精度 (cp118u 为 `rxPollMs`, 默认 10 ms); 引擎据此判断窗口是否可信 |
| `pins` | `[{channel, connectorId, pin}]` | 通过接线表把通道标成被测对象网络名 (如 `ai3` 显示为 `DUT.VREF`) |
| `writer` | 布尔 | 字节流是否注册了写回调, 决定 SDK 是否暴露 `transact` |

### 5.3 运行产物

现有 `runs/<runId>/` 下有 `plan.hhplan.yaml`、`wiring.json`、`events.jsonl`、`results.jsonl`、`summary.json`、`run.log`。新增:

- `streams/<hardwareId>.<streamId>.jsonl`: 原始数据, 每行一条记录, 含换算后的后端时间和设备原始时间。
- `streams/index.json`: 每路流的描述、时钟偏移估计、丢帧区间。
- `blobs/<sha256>`: blob 类型证据的内容。

`operation.*` 事件补充完整参数、`result`、`startedAt` / `completedAt` / `durationMs`、`streamRefs`。

## 6. 硬件服务 SDK 与适配器

### 6.1 分层契约 (D21, D22)

| 层 | 适配器要写什么 | 谁实现语义 | AI 适配可靠性 |
|---|---|---|---|
| **T0 必填** | `open` / `close` / `safe_state`、读写 `@tool`、参数范围、`pinout`、`sim.py` | 适配器 | 高。四块卡已验证, `check_adapter` 有确定性检查兜底 |
| **T1 声明流** | 一个同步 `sample()`; 或 `ByteStream` 加一个写字节回调 | SDK 负责轮询、时间戳、环形缓冲, 以及内置 `measure` / `wait_until` / `transact` | 高。比现状只多一行声明 |
| **T2 硬件定时采集** | 实现 `BlockSource` 协议: `start(rate, channels)` / `stop()` / `read_block() -> (t0, dt, samples)` | SDK 拼接时间轴、标记丢帧、降采样 | 中。第一家厂商由人写, 收进技能文档做样例, 后续 AI 照抄模式 |
| **T3 仪器自带测量/事务** | 直接暴露仪器工具, 如 SCPI `MEAS?`、协议栈的请求应答 | 适配器 | SCPI 类高 (文本协议, 模型友好); 二进制协议中 |

规则:

- 没有 T2 的卡, SDK 用软件轮询, 并如实声明 `timeResolutionMs`。不假装精确。
- 技能文档"不编造, 资料缺失写 TODO 或 `not_supported`"延伸为: AI 能确定的只做 T0 和 T1; T2、T3 按资料充分程度选做。
- 流只读、控制只走 MCP、`kind="actuate"` 不自动重发等硬性规则不变。

### 6.2 SDK 公共改动 (四个服务升级即得)

| 改动 | 做法 | 状态 |
|---|---|---|
| 调用关联 | `manager.invoke` 读 `_meta.operationId` 入 contextvar; `RingBuffer.append` 自动带 `op` | ⏳ |
| 结果回指 | 调用期间记录每路流被追加的 seq 范围, 工具返回附 `_meta.streamRefs` | ⏳ |
| 对时 | `hello` 帧、ping 回包加 `serverTime` | ⏳ |
| 描述扩展 | 5.2 的新字段 | ⏳ |
| 标记 | `Stream.mark(kind, detail)` | ⏳ |
| 内置 `<prefix>_measure(streamId, window, stat)` | 对任何 `scalar` / `bitmap` / `vector` 流按时间窗口算 `mean` / `min` / `max` / `p2p` / `last` / `count`, 等待数据覆盖到窗口终点; 返回样本 seq 范围 | ⏳ |
| 内置 `<prefix>_wait_until(streamId, condition, timeout_ms)` | 在设备端等待条件成立 (阈值、位、稳定时间), 返回成立时刻 | ⏳ |
| 内置 `<prefix>_transact(streamId, data, until, timeout_ms)` | 需要字节流注册 `writer`; 发送后等到分隔符 / 正则 / 字节数, 返回应答和设备端延迟 | ⏳ |
| `FrameStream` / `BlockSource` / blob 引用 | 5.1 新类型的参考实现与合规测试 | ⏳ |
| 写即发布 | 提供 `publish_after_write` 辅助: `actuate` 工具成功后立即向回读流写一条记录, 跳变沿出现在命令执行时刻而不是下一次轮询 | ⏳ |

### 6.3 四个适配器的调整

原则: 现有 `@tool` 名字、参数、返回不动; 全部是新增或内部改法。

**cp118u_i (多串口卡)**

- 已有收发字节流。`configure_port` / `clear_rx` / `flush` 调 `mark()`。
- 声明 `timeResolutionMs = rxPollMs`。
- 把 `_write` 注册为 `serialN` 的 `writer`, 自动获得 SDK 的 `transact`, 串口诊断类测试 "发命令、等待、读缓存" 三步压成一步, 延迟在设备端测。

**pci1710l (多功能采集卡)**

- 性能问题必须改: `_sample_bits` 采一次 DI/DO 要 16 次 hwcli 往返 (`adapter.py:125-131`); 16 路 AI 是 16 个独立采样流, 每次采样单独拿设备锁, 16 路 10 Hz 就是每秒 160 次锁竞争, 会拖慢测试步骤, 且各通道不同步。
- hwcli 增加按端口一次读 16 位的命令。
- 新增 `vector` 流 `ai`, 一次扫描所有已配置通道; `ai0..15` 保留兼容。
- `set_level` 成功后立即向 `do` 流发布。
- 后期 (T2): 用板卡硬件定时采集加 FIFO 实现 `BlockSource`, 突破软件轮询 100 Hz 上限。由人先写。

**pci1762 (继电器输出卡)**

- 同 1710l, 按端口一次读。
- `set_relay` / `set_bank` 成功后立即向 `relay` 流发布。
- `di` 流开启 `publish_on_change` 并提高采样率; 现状 5 Hz 轮询会漏窄脉冲。
- 声明 `relay` 流 `source = readback`; 现状只写在 description 里, 界面读不到。

**pci6208v (模拟量输出卡)**

- 基本不改。声明 `ao0..7` 的 `source = shadow`、`range = [-10, 10]`。
- 无回读能力; 要看实际输出, 靠接线表把它接到 1710l 的 AI, 示波器里两条曲线叠加对比。

## 7. 测试引擎: 判定语义 (D23, D24)

### 7.1 为什么不能用"最新值"

1. **最新值是旧的**: 滞后一个采样周期、网络传输和 WS 攒批 (50 ms)。
2. **可能误判通过**: 先设 3.3 V 再判定 3.3 V 附近, 若上一轮也是 3.3 V, 残留旧值会让新激励未生效的步骤通过。现状"调用一次读一次"天然保证读数在激励之后, 改为订阅后这层保证消失。
3. **丢帧 / 断线**必须判"证据缺失", 否则是假通过。

### 7.2 测量窗口步骤

新增步骤类型 `Measure` (或 `InvokeTool` 的一种模式), 语义是**相对激励的时间窗口测量**:

```yaml
- InvokeTool: pci6208v.set_voltage(channel=1, volts=3.3)   # 返回设备端完成时刻 t_act
- Measure:
    stream: pci1710l/ai3
    window: { from: t_act + 100ms, to: t_act + 150ms }      # 替代 "延时 100ms + read_voltage"
    stat: mean
    assert: 3.267 <= mean <= 3.333 and p2p < 0.010
```

- 引擎等到该流的数据覆盖窗口终点再计算; 用到的样本段作为证据保存 (`streamRefs`), 运行页示波器高亮该窗口, 事后可用录制数据复判。
- 同一设备内的窗口优先下发给设备端 `measure` (T1 内置); 跨设备在后端用订阅数据算。
- 证据来源可以是 SDK 窗口统计, 也可以是仪器自带测量值 (T3), 两者都作为 `measurement` 结果。
- 流不存在或分辩率不足时, 退回"延时 + 读一次", 并在结果里标注证据等级。旧方案完全兼容。

### 7.3 跨设备窗口与对时

- `StreamHub` 对每台设备服务估算时钟偏移 `offset ± err`。
- 窗口起点按"后端收到激励返回的时刻"换算, 再加 `err`, 保证窗口一定落在激励之后。
- 要求稳定时间远大于 `err` (如 100 ms 对 1 ms); 引擎在静态校验中提示窗口过窄。

### 7.4 引擎其他改动

- `invoke_device` 记录完整参数、`startedAt` / `completedAt`、`streamRefs`, 事件 `operation.dispatched` / `operation.succeeded` 相应扩展。
- 运行开始时, 按方案涉及的硬件订阅相关流 (`RunStreamRecorder`); 结束后停止。
- 新增 `readRunStream(runId, streamId, t0, t1, maxPoints)`, 返回前按 min/max 降采样。
- 数据推送走独立通道 `testRunIo`, 50 ms 攒批, 不混入现有 `testRun` 事件流。

## 9. 运行台 UI/UX

### 9.1 定位

把"运行日志"页改为"运行"页 (运行台)。主流程: 设备 → 接线 → 编排 → **运行** → 历史。运行台同时服务实时监控和事后复盘, 两种模式一个界面。启动运行后自动跳转; 方案页顶部显示"运行中 → 查看"; 批量运行时左侧显示批量队列。方案页不再内嵌运行日志。

### 9.2 布局

```
┌ 运行头: #12 方案A ● 运行中 03:21  ▰▰▰▱▱ 18/30   [暂停][中止]   [实时●|回放]  [历史▾][导出] ┐
├──────────────┬────────────────────────────────────────────────────────────────┤
│ 步骤树        │ 时间轴 ─────────────────────┃────────────── (缩放/拖动, ┃=时间游标) │
│ ▾ 测试       │ 步骤   ▇准备▇ ▇设K3▇▇读串口▇ ▇判定▇                                │
│   ✓ 设K3     │ AI3    ~~~╱‾‾‾‾╲____   ░窗口░           3.28 V  DUT.VREF          │
│   ● 读串口 ← │ DI2    __┌────┐_____                     1                        │
│   ○ 判定     │ AO1    - - - - - - - - (影子, 虚线)      5.00 V                   │
│              ├────────────────────────────────────────────────────────────────┤
│ 证据/结果     │ 终端 [P1▾][HEX|ASCII][仅本步骤][跟随]                          │
│ (选中步骤)    │ 03:21.114  TX  设K3→读串口  55 AA 01 03                        │
│              │ 03:21.131  RX              "OK\r\n"            ⚠ 丢失 12 帧    │
└──────────────┴────────────────────────────────────────────────────────────────┘
```

### 9.3 交互规则

- **一条时间轴联动所有视图**: 选中步骤, 时间轴定位、终端只显示该步骤帧、示波器高亮测量窗口; 在波形上拖游标, 步骤树和终端同步。操作方式类似逻辑分析仪。
- **仪器按流描述自动生成**: `bytes` / `frame` 进终端, `scalar` / `bitmap` / `vector` / `block` 进示波器, `blob` 进证据附件。运行开始按方案涉及的硬件生成默认布局, 用户调整后按方案保存。不为每种板卡写界面代码。
- **失败先给结论**: 自动定位第一个问题步骤, 展开其收发帧和测量窗口。
- **丢帧显式标出**: `gap` 显示为"丢失 N 帧", 不静默。
- **运行中终端只读** (D25); 手动页复用 `Terminal` / `Scope` 组件并允许发送。

### 9.4 渲染实现

- 示波器: Canvas, 引入 uPlot (约 45 KB); 数字量阶梯、模拟量折线、多通道共用时间轴; 界面端只拿降采样数据。
- 终端: 虚拟列表; 每行时间戳、方向 (TX/RX 配色)、HEX/ASCII、所属步骤; 按设备过滤、跟随开关。
- 统一 `useStream(source, from)` 封装 D18 的日志 + 游标模型。
- 模块: `features/instruments/` (`useStream`、`Scope`、`Terminal`、`InstrumentDock`、布局模型), `features/runs/` (`RunConsolePage`, 从 testing 移出; 时间游标状态)。

## 10. 评估

### 10.1 本地模型完成硬件适配的可靠性

可靠性主要来自约束和检查, 不是模型本身。现有做法是正确路线: 技能文档给流程, 骨架脚本给起点, 四个参考适配器给样例, `check_adapter` 做确定性验证, 模拟器让干跑就能测。在此框架下, 本地开源模型写 200 行 ctypes 封装加影子寄存器模拟器是稳的。

会出问题的三类工作, 处理方式:

| 风险 | 处理 |
|---|---|
| 并发 (读线程与 `io_lock`) | T1 收进 SDK, 适配器只剩同步函数 |
| 时序 (时间戳、丢帧、窗口边界) | 全部由 SDK 承担 (D21, D26) |
| 厂商硬件定时采集 (DMA / FIFO / 触发) | T2 可选; `check_adapter` 增加时序合规测试 (模拟器上验证 `t` 单调、`dt` 一致、溢出产生 `gap`); 第一块卡由人写作为样例 |

技能文档需同步升级: 分层说明、T1 一行声明示例、`FrameStream` / `BlockSource` 参考实现、时序合规检查项。

### 10.2 新语义覆盖的测试资源范围

| 资源类型 | 需要的原语 | 现状 | 缺口 |
|---|---|---|---|
| 模拟采集、温度、DMM | `scalar` 采样流 | 有 | 无 |
| 离散输入 | `bitmap` 采样流, 变化才记录 | 有 | 无 |
| 继电器、离散输出、模拟输出、程控电源 | 写即发布 | 有 | 写入时补一条发布 |
| 串口、TCP 透传 | `bytes` 流加 `writer` | 有 | SDK 通用 `transact` |
| CAN、LIN、SPI 事务 | `frame` 流 | 无 | `FrameStream` |
| 示波器、硬件定时采集 | `block` 流 | 无 | T2 `BlockSource` |
| 信号发生器、程控负载 | 配置型写工具 | 有 | 无 (本身不产生数据) |
| 摄像头、示波器截图、日志文件 | `blob` 证据引用 | 无 | blob 类型 |
| 固件烧写 (FireDAP) | 长任务进度 | 旧布局, 独立 | 进度流 |
| SCPI 仪器 (`MEAS?`, `READ?`) | T3 仪器自带测量 | 可用现有 `read` | 引擎接受仪器测量值作为窗口证据 |

补上 `frame`、`block`、`blob` 三种类型后, 汇报材料中"接入示波器、信号发生器等任意硬件设备"在数据模型上成立。

## 12. 风险

| 风险 | 应对 |
|---|---|
| 数据量: 16 路 AI 长时间运行 | 落盘原始数据, 界面只取降采样; 环形缓冲容量按采样率配置; 录制文件按大小滚动 |
| 时钟偏移估算不准导致跨设备窗口错位 | 窗口起点取保守值; 静态校验提示窗口过窄; 单设备条件优先在设备端算 |
| 采样与工具调用竞争设备锁 | 1710l / 1762 一次读全部位; `vector` 流一次扫描; T2 后采样不再经过锁 |
| 旧版本设备服务无 `op` 标记 | 后端退回按时间窗口匹配, 并在证据中标注"时间匹配" |
| 模拟器看不出效果 | `sim.py` 支持连续信号 (如 AO 设定值经一阶响应回到 AI), 演示用噪声按环境变量开启, 与技能文档现有约定一致 |
| 契约变大削弱 AI 适配 | 严守 T0 不变; 新能力全部可选并有 SDK 默认实现 |
