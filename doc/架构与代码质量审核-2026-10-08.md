# 架构、代码质量、数据结构与算法审核

审核日期：2026-10-08。代码基线：`4072e11`，开始审核时工作区无修改。

## 结论与范围

现有 Electron/React → HTTP/SSE → Python 应用/领域/资源层 → 设备 SDK 的结构适合单机测试台架；没有发现需要整体重写的依据。操作注册表生成契约、解释器通过端口访问外部资源、纯判定器、SQLite 运行日志以及插件隔离，都是值得保留的设计。

主要问题集中在跨层数据语义：流记录的所有权、证据类型的传递、游标的单调性，以及项目会话与运行缓存的生命周期。已有测试多数覆盖单个模块，仍遗漏了真实 SDK 共享对象、多消费者、长时间空闲和切换项目等组合场景。

本次确认 7 项缺陷，其中 2 项 P1、5 项 P2。P1 建议优先修复；P2 应安排修复并补回归测试。审核未修改生产代码，只新增本报告。

重点阅读范围：前后端边界及依赖规则、设备生命周期与插件传输、流缓冲/录制/存储/显示、计划解释器与运行状态、协议分帧与派生数据、判定算法。第三方库、板卡固件资料未逐文件审计；没有进行真实板卡测试、端到端 UI 测试、发布构建或长时间负载测试。

## 已确认缺陷

### 1. [P1] 临时判定丢失证据声明，把设定值影子当作测量证据

位置：[streams/store.py:434](E:/Project/testStand/app/python/src/teststand_backend/streams/store.py:434)、[streams/live.py:236](E:/Project/testStand/app/python/src/teststand_backend/streams/live.py:236)。

`StreamRecorder` 保存了 `hello.declaration`，但 `StreamStore.stream_data()` 构造 `StreamData` 时未传入 `descriptor`。临时 `observe`/`expect` 直接使用该结果，判定器因此无法看到 `kind: setpoint`。正式运行的 `RunIO.read_data()` 会补充声明，所以两条入口行为不一致。

已通过完整 `LiveStreams.observe()` 路径复现：假设备声明 scalar 流 `kind: setpoint`，在 250 ms 内持续发布 1.0，对 `mean == 1.0` 判定，实际返回 `verdict: pass, evidenceType: T1`。同样的数据显式携带声明时，判定器正确返回 `inconclusive`。该路径也由 Agent 的临时观测工具使用。

影响：软件写入值可能被当作物理测量的通过证据，违反项目“设定值影子不用于通过/失败判定”的约束。

建议：由存储读取接口统一恢复完整流声明，使调试、正式运行、重新判定使用一致的 `StreamData`；补 `observe` 和 `expect` 的 setpoint 集成测试，而不只测试纯判定器。

### 2. [P1] 多个录制器原地修改 SDK 记录，污染其他录制数据库的 ID

位置：[streams/recorder.py:82](E:/Project/testStand/app/python/src/teststand_backend/streams/recorder.py:82)、[streams/store.py:191](E:/Project/testStand/app/python/src/teststand_backend/streams/store.py:191)、[ringbuffer.py](E:/Project/testStand/devices/sdk/src/teststand_device_sdk/ringbuffer.py)。

`RingBuffer.read()` 返回缓冲区内字典的引用。进程内设备将这些对象直接交给流源，录制器随后写入 `record["i"]`。实时查看与测试运行同时录制同一流时，两个数据库共用记录对象。第二个数据库的 `append()` 又未从 payload 排除已有 `i`；读取时 `_row()` 用 payload 覆盖真实数据库 ID。

最小复现：数据库 A 已有 5 行，将共享记录编号为 6；数据库 B 插入同一 SDK 记录，真实主键为 1，但 `records()` 返回 `i = 6`，`last_i()` 返回 1。后续分页若使用返回的 6，会跳过 B 中 ID 2～6 的记录。

影响：正常的“显示流 + 运行录制”组合即可污染记录身份，造成分页遗漏、重复或游标不一致。现有后端假设备在读取时复制字典，恰好遮蔽了真实进程内 SDK 的行为。

建议：在读取或录制边界生成消费者私有记录；明确区分 SDK 的 `seq` 与数据库的 `i`，持久化 payload 排除所有保留元数据，读取时也禁止 payload 覆盖身份字段。补真实 SDK 环形缓冲与两个录制器的集成测试。

### 3. [P2] 缓存淘汰后 SQLite 复用主键，增量订阅漏掉新报文

位置：[streams/store.py:625](E:/Project/testStand/app/python/src/teststand_backend/streams/store.py:625)、[streams/live.py:333](E:/Project/testStand/app/python/src/teststand_backend/streams/live.py:333)。

实时缓存按时间删除全部旧记录，表主键是 `INTEGER PRIMARY KEY`，未保证删除后的编号持续增长。串口/报文消费者则长期保存 `after`，只读取 `i > after`。

已复现：消费者读到 ID 5，淘汰全部记录，再追加新报文，新主键为 1；经过实际 `_entry()` 增量路径返回的 `records` 为空。默认保留期是 10 分钟，因此持续订阅的低频串口在长时间无消息后存在该问题。

建议：使用独立单调序号或 `AUTOINCREMENT`，或显式引入缓存 epoch 并在变化时重置客户端游标。测试应覆盖缓存清空后恢复发布，而不只是持续采样。

### 4. [P2] 运行缓存未按项目隔离，切换项目后返回旧项目结果

位置：[testing/engine.py:127](E:/Project/testStand/app/python/src/teststand_backend/testing/engine.py:127)、[application/services.py:450](E:/Project/testStand/app/python/src/teststand_backend/application/services.py:450)。

`TestEngine` 在后端生命周期内复用；`runs`、`recordings` 不随项目切换清理。`current()` 优先返回内存中最近一次运行，`get()` 也先查内存。持久层路径却取自当前项目，形成跨项目混合状态。

已复现：在项目 A 完成空计划，切换到已初始化但没有历史记录的项目 B，B 的持久化 `latest_run()` 为 `None`，`engine.current()` 仍返回 A 的计划和 runId。项目切换通知路径未重建或清理测试引擎。

影响：B 的界面可能展示 A 的结果；旧运行快照与当前项目的操作表、录制路径不匹配。

建议：把运行/批次缓存归属到明确的项目会话，切换时清理或重建，读取时校验项目身份。对 `BatchCoordinator.active` 一并检查。补 A→B、离开项目、重新打开项目的用例。

### 5. [P2] 互相关峰值插值使用无穷邻点，合法输入返回 NaN

位置：[streams/judge.py:886](E:/Project/testStand/app/python/src/teststand_backend/streams/judge.py:886)。

`_pearson()` 将少于 3 对样本的 lag 标记为 `-inf`，搜索范围却允许只剩 2 对样本的边缘 lag。某个有效最优峰邻接该位置时，抛物线细化直接使用 `-inf`，导致 `inf / inf`，最终延迟为 NaN。

已复现：10 个等间隔有限数值样本，`maxLagMs = 100`，得到相关系数 `0.7932606232059289`，但 `delayMs = NaN`。输入可用 `random.Random(0)` 连续生成两组 10 点信号对，取第二对重现。4 点输入也能复现。

影响：delay/phase 判定变成无效值或 inconclusive；传输层将非有限数值转换为 null，进一步隐藏算法错误。

建议：插值前要求三个相关分数均有限，并保证有效重叠样本数；邻点无效时保留离散峰值。增加窄窗口、较大 maxLag、恒定子区间及边缘峰值测试。

### 6. [P2] 实时订阅合并静默截断，超过 64 路的控件永远收不到数据

位置：[live-hub.ts:38](E:/Project/testStand/app/apps/desktop/src/renderer/features/signals/live-hub.ts:38)。

前端把所有控件所需的流合并后直接 `.slice(0, MAX_LIVE_KEYS)`。后端 64 路限制是每个订阅的限制，当前实现却将它变为整个画布的隐性限制，没有分片或向受影响控件返回错误。

已执行该 TypeScript 模块的实际转译结果：注册 65 个单流消费者，上游只收到 64 个 key，`H__s64` 被排除。

建议：将 key 分组建立有界数量的上游订阅，或在画布配置时明确校验上限并给出错误。不要将缺少订阅伪装成设备没有数据。

### 7. [P2] 契约生成检查未处理 Windows 换行符，正常检出也无法通过测试

位置：[generate-openapi-types.mjs:25](E:/Project/testStand/app/packages/contracts/scripts/generate-openapi-types.mjs:25)。

生成器用 LF 输出并与文件逐字符比较。当前仓库 `core.autocrlf=true`，`openapi.generated.ts` 的 Git 内容为 LF，工作区为 CRLF，且没有相关行尾属性约束。

`pnpm test` 实际失败于 “openapi.generated.ts is stale”。重新在内存生成后核对：原始文本不相等，双方统一行尾后完全相等；没有契约内容漂移。

影响：Windows 正常检出后整体验证失败，并阻止递归测试继续执行桌面包。

建议：用 `.gitattributes` 固定生成文件为 LF，或比较前仅归一化 CRLF。不要通过反复重生成来掩盖检出行为。

## 架构与数据结构改进建议

以下是结构与复杂度分析，未进行真实硬件性能压测，不等同于已测得性能故障。

| 方面 | 现状与判断 | 建议 |
|---|---|---|
| 服务分层 | Python 4 项依赖契约通过；前端 327 个模块、1335 条依赖无违规 | 保留现有层次，优先修复层间语义，而不是重新拆微服务 |
| 核心记录模型 | 大量 `dict[str, Any]` 同时承载设备原始数据、录制元数据、判定输入；严格 mypy 无法发现这些字段污染 | 优先为 RawRecord、RecordedRecord、StreamDescriptor、项目会话定义明确类型和转换函数；不必一次替换全部字典 |
| 运行生命周期 | 已结束的解释器仍保存在 `engine.runs`；解释器持有完整 events/results，`recordings` 也持续积累 | 完成后从 SQLite 读取历史；内存仅保留活动运行和有界近期缓存，并统一项目切换时的释放 |
| 环形缓冲 | deque 的尾部追加/头部淘汰为 O(1)，适合写入；`islice` 读取接近尾部的游标仍需跳过前缀，seek 为线性扫描 | 默认 4096 容量下可以保留；扩大容量或增加读者前先测量，再考虑固定数组按 seq 寻址及时间索引 |
| 派生协议视图 | `DerivedViews.decoded()` 缓存键包含不断变化的 watermark，失效后读取并重新解码全部原始记录；最多保留 8 个完整版本 | 区分数据版本和水位线版本，以 lastI/epoch 增量解码；避免一个流保留多份完整历史。持续录制每次刷新全量回放的累计代价会随历史增长 |
| 波形查询 | SQL 时间索引合理，但先在 Python 展开窗口所有 block 样本，再降采样；maxPoints 只限制输出，不限制中间内存和计算量 | 对大窗口进行分块聚合或预聚合，保留 min/max；原始证据仍完整存储 |
| 互相关 | 直接搜索复杂度 O(N×L)，N 限制为 1024，避免了无界增长 | 先修数值稳定性；批量调用前测量事件循环延迟，需要时移至工作线程或采用向量化/FFT |
| SQLite 资源 | `RuntimeStateStore._connect()` 每次新建连接；`with connection` 管理事务，不负责 close | 使用显式关闭的上下文管理器或会话级连接管理，避免把释放时机交给 GC |
| 分层规则覆盖 | 前端 feature 隔离规则列举了较早的功能目录，未覆盖 testing/signals/bench 等全部当前目录 | 根据当前架构补齐规则，防止新功能绕过约束 |

另一个需要补用例的缓存语义：淘汰前的最后一个 bits/设定值代表仍生效的状态，不能简单随时间一起删除。应区别“事件过期”和“当前电平锚点”。
