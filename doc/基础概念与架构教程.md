# 第一部分 硬件与测量

## 1. 测试台由什么组成

一个自动化测试台通常有五样东西：

```
┌──────────────┐    网络     ┌──────────────────────────────┐   线缆/接线   ┌──────────┐
│  测试终端     │ ◄────────► │ 工控机（测试资源服务器）        │ ◄──────────► │ 被测产品  │
│ 操作员用的电脑 │            │ 插着板卡，连着仪器              │              │  (DUT)   │
│ 编计划、看结果 │            │ 采集卡 / 继电器卡 / 串口卡 / 电源 │              │          │
└──────────────┘            └──────────────────────────────┘              └──────────┘
```

| 名词 | 含义 | 例子 |
|---|---|---|
| **被测产品（DUT）** | 要被测试的东西，Device Under Test 的缩写，也叫 UUT（Unit Under Test） | 一块控制板、一个显示模块 |
| **测试资源** | 用来给 DUT 施加激励、测量响应的设备 | 电源、电子负载、采集卡、继电器卡、串口卡、总线卡 |
| **工控机** | 安装测试资源的工业计算机，板卡插在它的主板插槽里 | 研华 IPC、PXI 机箱 |
| **接线/工装** | 把测试资源的端子接到 DUT 引脚的线缆和转接板 | 转接箱、测试夹具 |
| **测试终端** | 操作员使用的软件和电脑，编写测试计划、启动测试、查看结果 | HardwareHarness 桌面应用 |

"终端"这个词在不同场合意思不同，本项目中的用法：

- **测试终端**：操作员面前运行 HardwareHarness 桌面应用的电脑和软件。
- **终端（Terminal）视图**：运行台里显示串口实时收发内容的文本窗口，类似串口调试助手。
- **命令行终端**：PowerShell、cmd 这类输入命令的窗口。

测试的基本动作永远是一个循环：**设定 → 等待 → 采集 → 判定 → 恢复**。例如"给 DUT 供 28 V，等 500 ms，测它输出口电压，判断在 4.9～5.1 V 之间，最后关电源"。

## 2. 总线：设备之间传数据的公共通道

**总线（Bus）** 是多个设备共享的一组信号线加一套通信规则。可以把它想成一条公路：设备是路边的房子，规则决定谁什么时候能上路、货物怎么打包、地址怎么写。

"总线"在本项目里出现在两个层面：

| 层面 | 作用 | 例子 |
|---|---|---|
| **计算机扩展总线** | 让 CPU 和插在主板上的板卡交换数据 | PCI、PCIe、PXI、cPCI、USB |
| **设备通信总线** | 让测试台和 DUT，或者 DUT 内部模块之间通信 | RS422、CAN、ARINC 429、MIL-STD-1553B、IEEE 1394 |

**PCI**（Peripheral Component Interconnect，外设部件互连）是 1990 年代起 PC 主板上的扩展插槽标准，是 32 位并行总线。

- **PCIe**：它的串行高速后继者。
- **PXI**：在 cPCI（CompactPCI）基础上加了触发和同步线的测控机箱标准。

资料中的 THC 系列、研华 PCI-1710L 等采集卡，就是插在这类插槽里的板卡。

板卡插上后，CPU 有两种方式和它交换数据：

- **寄存器读写**：板卡把一段地址空间映射给 CPU（叫 BAR，Base Address Register），CPU 读写这些地址就是读写板卡的寄存器。
- **DMA**（Direct Memory Access，直接内存访问）：板卡自己把大量数据搬进主机内存，搬完再通知 CPU，适合高速采集。

资料中的 PLX 相关代码（`PlxPci_PciBarSpaceRead`、`PlxPci_DmaTransferUserBuffer`）就是直接做寄存器和 DMA 操作。这很底层、很容易出错，所以正常情况下由厂商驱动包起来。

> 延伸阅读：维基百科 "Peripheral Component Interconnect"、"Direct memory access"；NI 的 PXI 平台介绍。

## 3. 驱动、SDK 和 DLL

应用程序不直接碰硬件，中间有几层：

```
你的程序（Python 适配器）
   │  调用函数，例如 THC031B_GetValue(handle, ch, &value)
   ▼
厂商 SDK：DLL（动态链接库）+ 头文件 .h + 导入库 .lib
   │  把"读通道 3 的电压"翻译成寄存器操作
   ▼
内核驱动（.sys）：唯一被允许直接访问硬件的代码
   │
   ▼
板卡硬件
```

| 名词 | 解释 |
|---|---|
| **驱动（Driver）** | 运行在操作系统内核里、直接操作硬件的程序。安装板卡时装的就是它 |
| **SDK**（Software Development Kit，软件开发工具包） | 厂商给开发者的函数库、头文件、文档和例子 |
| **DLL**（Dynamic Link Library，动态链接库） | Windows 上可以被多个程序在运行时加载的函数库文件 |
| **头文件（.h）** | 用 C 语言写的函数声明和数据结构定义，告诉你函数叫什么、参数是什么类型 |
| **ctypes** | Python 标准库，可以直接加载 DLL 并调用其中的 C 函数；本项目的适配器就用它（或者一个小的命令行程序）调用厂商 SDK |
| **句柄（Handle）** | `OpenDevice` 返回的一个编号，之后的调用都拿它指明操作哪块卡 |
| **回调（Callback）** | 你把一个函数交给 SDK，SDK 在数据到达时反过来调用它；例如 THC001B 的 `SampleCallBackRegister`、1394 卡的接收回调 |

厂商 SDK 的函数几乎都遵循同一个套路：`Open → 配置 → 读/写（重复）→ Close`。这也是为什么 AI 能比较稳定地照着头文件写出适配器：模式固定，只是函数名和参数不同。

> 延伸阅读：Python 官方文档 `ctypes`；微软文档 "Dynamic-Link Libraries"。

## 4. 信号：模拟量和数字量

| 类型 | 缩写 | 含义 | 例子 |
|---|---|---|---|
| 模拟输入 | AI | 测量一个连续变化的电压/电流 | 采集卡读 DUT 输出的 4.98 V |
| 模拟输出 | AO | 输出一个可设定的电压/电流 | DA 卡输出 2.5 V 模拟传感器 |
| 数字输入 | DI | 读取高/低电平（1/0） | 读一个开关是否闭合 |
| 数字输出 | DO | 输出高/低电平 | 控制一个指示灯、一个继电器线圈 |
| 继电器/矩阵 | — | 机械或固态开关，接通或断开一条通路 | 把采集卡通道 1 切到 DUT 的 A 点或 B 点 |

几个关键指标：

- **量程**：能测/能输出的范围，例如 ±10 V。
- **分辨率**：能区分的最小变化。16 位 ADC 在 ±10 V 量程下，分辨率约为 20 V / 65536 ≈ 0.3 mV。
- **精度**：测得值和真实值的接近程度，受增益误差、偏置误差、噪声影响，通常比分辨率差得多。
- **采样率**：每秒采多少个点，单位 Hz 或 S/s。
- **单端/差分**：单端测"信号对地"的电压；差分测"两根线之间"的电压，抗干扰更好。

**奈奎斯特定理**：要从采样点还原一个频率为 f 的信号，采样率必须大于 2f。实际上想看清波形形状，一般要 5～10 倍以上。

数字量常常"成组"出现。例如 96 路 DO 可以用一个整数的二进制位来表示，第 n 位是 1 就表示第 n 路为高。这就是本项目 **bits 流** 用一个 `mask` 整数表示一组数字状态的原因。

> 延伸阅读：NI 白皮书 "Data Acquisition (DAQ) Fundamentals"；维基百科 "Nyquist–Shannon sampling theorem"；《The Art of Electronics》第 13 章（数模转换）。

## 5. 波形

一个周期信号用下面这些量描述：

```
  电压
   ▲      ┌────┐    ┌────┐          幅值（Amplitude）：峰值离中心线多高
 A │      │    │    │    │          偏置（Offset）：中心线离 0 V 多高
   │──────┼────┼────┼────┼── 偏置    周期 T：一个完整波形的时间
   │      │    │    │    │          频率 f = 1 / T，单位 Hz
   │ ─────┘    └────┘    └───        占空比（Duty）：高电平时间 / 周期
   └───────────────────────► 时间    相位（Phase）：两个同频信号在时间上错开多少，用角度表示
          |<-- T -->|
```

| 指标 | 含义 | 正弦波的关系 |
|---|---|---|
| 峰峰值 Vpp | 最大值减最小值 | 2A |
| 有效值 RMS | 与它发热相同的直流电压 | A / √2 ≈ 0.707A |
| 平均值 | 一个周期内的平均 | 偏置 |

**波形怎么输出？** 分两种设备：

1. **静态 DA 卡**（例如 PCI-6208V）：每调用一次"设电压"就改变一次输出，之后保持不变。想输出波形，只能由软件定时反复调用。时间精度受操作系统调度影响，通常是毫秒级抖动，只适合很慢的波形。
2. **任意波形发生器（AWG）或带 FIFO 的 DA 卡**：先把一整个周期的采样点下载到板卡内存，再由**板卡自己的硬件时钟**按固定速率逐点输出，可以一直循环。时间精度由晶振决定，可以到纳秒级。

所以网络另一端的软件**不能**逐点推送波形。网络延迟和抖动是毫秒级的，推过去的波形会变形。正确做法是把"波形参数"或"一整段采样点"交给离硬件最近的一方，由它按硬件时钟输出。本项目的设计就是这样定的（设计文档第 5.6 节）。

> 延伸阅读：Tektronix "Fundamentals of Arbitrary Waveform Generators"；维基百科 "Root mean square"、"Duty cycle"。

## 6. 串口

**串口**一次只传一个比特，按顺序一位一位发。最常见的是 **UART**（通用异步收发器）。一个字节在线上的样子：

```
空闲(高) 起始位  D0 D1 D2 D3 D4 D5 D6 D7  [校验位]  停止位  空闲
 ───────┐     ┌──┬──┬──┬──┬──┬──┬──┬──┬───────┬──────────
        └─────┴──┴──┴──┴──┴──┴──┴──┴──┘
```

双方必须事先约定参数，常写成 `115200 8N1`：

| 参数 | 含义 |
|---|---|
| 波特率 | 每秒多少位，例如 9600、115200、500000 |
| 数据位 | 通常为 8 |
| 校验 | N（无）、E（偶）、O（奇），用来发现单比特错误 |
| 停止位 | 1 或 2 |

同样的 UART 数据，可以用不同的**电气标准**在线上传输：

| 标准 | 电平方式 | 连接方式 | 典型距离 | 资料中的用途 |
|---|---|---|---|---|
| RS232 | 单端，±3～15 V | 点对点、全双工 | ≈15 m | 电源、视频矩阵、DUT 调试口 |
| RS422 | 差分 | 一发多收、全双工 | ≈1200 m | DUT 命令口、测试口、28 V 电源 |
| RS485 | 差分 | 多点总线、通常半双工 | ≈1200 m | 多节点通信 |

串口最重要的特点：**它是字节流，没有"消息"边界**。你发了 "HELLO\r\n"，对方可能分两次收到 "HEL" 和 "LO\r\n"。所以要靠约定来切分消息：

- 文本协议用换行符切分；
- 二进制协议用"帧头 + 长度 + 数据 + 校验"切分（见第 9 章）。

本项目把串口收发建模为 **bytes 流**：每条记录是一段字节，带方向（`tx` 发送、`rx` 接收、`mark` 标注）和时间戳，不替你切分消息。

> 延伸阅读：pySerial 文档；TI 应用笔记 "RS-422 and RS-485 Standards Overview and System Configurations"（SLLA070）；维基百科 "RS-232"。

## 7. 仪器控制：VISA 和 SCPI

台式仪器（电源、万用表、示波器、电子负载）大多用文本命令控制。

**SCPI**（Standard Commands for Programmable Instruments，可编程仪器标准命令）规定了命令的格式。它是树状结构，冒号分层，问号表示查询：

```
*IDN?                 → "ITECH,IT6952A,6000xxxx,1.02"   查询身份（IEEE 488.2 公共命令）
*RST                  复位
VOLT 28.0             设定电压 28 V
CURR 2.0              设定限流 2 A
OUTP ON               打开输出
MEAS:VOLT?            → "27.998"   测量实际输出电压
MEAS:CURR?            → "0.513"
```

**VISA**（Virtual Instrument Software Architecture，虚拟仪器软件架构）是一套统一的"打开仪器、写、读"接口，屏蔽了 USB、网口、GPIB、串口的差别。它用资源字符串区分连接方式：

```
USB0::0x2EC7::0x6950::800123456::INSTR     USB 连接
TCPIP0::192.168.1.20::inst0::INSTR         网口连接
ASRL3::INSTR                               串口 COM3
```

Python 里用 **PyVISA** 调用 VISA：

```python
import pyvisa
rm = pyvisa.ResourceManager()
psu = rm.open_resource("USB0::0x2EC7::0x6950::800123456::INSTR")
print(psu.query("*IDN?"))
psu.write("VOLT 28.0"); psu.write("OUTP ON")
print(float(psu.query("MEAS:VOLT?")))
```

SCPI 仪器的适配对 AI 来说最可靠：命令就写在手册里，是文本，一问一答，能直接用 `*IDN?` 验证连通。有些设备（例如资料里的电源调理板、ZT DA/TTL 模块）用厂家自定义的二进制协议，就要照着协议文档组帧、算校验。

> 延伸阅读：IVI Foundation 的 SCPI-99 标准文本；PyVISA 文档；任一台 ITECH/RIGOL 电源的编程手册。

## 8. 消息型总线：CAN、ARINC 429、1553B、1394

和串口不同，这些总线**天生以"消息"为单位**，每条消息有明确的身份标识和数据。本项目把它们建模为 **frames 流**：每条记录是 `{t, dir, id, data}`。

| 总线 | 一条消息长什么样 | 身份标识 | 典型速率 | 常见领域 |
|---|---|---|---|---|
| **CAN** | ID + 0～8 字节数据（CAN FD 可到 64 字节） | 11 位或 29 位 ID | 125 k～1 Mbps | 汽车、工业 |
| **ARINC 429** | 一个 32 位字：label（8 位）+ SDI（2 位）+ 数据（19 位）+ SSM（2 位）+ 奇校验（1 位） | label（通常用八进制写）+ SDI | 12.5 k 或 100 kbps | 民用航空电子 |
| **MIL-STD-1553B** | 命令字 + 最多 32 个数据字 + 状态字，每字 16 位有效数据 | RT 地址（0～31）+ 收/发 + 子地址（0～31）+ 字数 | 1 Mbps，双冗余 | 军用航空 |
| **IEEE 1394**（航空用 AS5643） | 异步包、等时包，按帧周期（STOF）发送 | 节点、通道、消息类型 | 100～400 Mbps | 航空、工业相机 |

### 1553B 的三种角色

1553B 有三种角色，它们的工作方式决定了为什么总线卡的适配很难：

- **BC**（Bus Controller，总线控制器）：总线上唯一的"指挥"，按调度表轮流点名。
- **RT**（Remote Terminal，远程终端）：被点名才回答，最多 31 个。
- **BM**（Bus Monitor，总线监视器）：只听不说，记录总线上的所有消息。

测试台的总线卡通常要扮演 BC（去问 DUT）或 RT（模拟 DUT 的邻居），还要做 BM（记录证据）。这需要配置调度表、消息缓冲区、中断，比"读一个电压"复杂得多。

### 消息身份的编码

frames 流的 `id` 是一个整数。不同总线要约定把各自的身份字段压成一个整数，约定见设计文档第 5.4 节，例如：

- CAN：`id` 就是 CAN ID；
- ARINC 429：`id = SDI << 8 | label`；
- 1553B：`id = RT << 11 | TR << 10 | 子地址 << 5 | 字数`，也就是命令字本身。

> 延伸阅读：
> - CAN：python-can、cantools 文档；Bosch CAN 2.0 规范。
> - ARINC 429：AIM 或 Excalibur 的 "ARINC 429 Tutorial"。

## 9. 帧、校验和 ICD

### 帧

**帧（Frame）** 是二进制协议里的一条完整消息。一个典型的串口二进制帧：

```
 字节:  0     1     2      3      4 .. 4+N-1   4+N
      ┌─────┬─────┬──────┬──────┬───────────┬──────┐
      │ 0xAA│ 0x55│ 长度N │ 命令  │  数据       │ 校验  │
      └─────┴─────┴──────┴──────┴───────────┴──────┘
       帧头（同步字）                             sum8 / xor / CRC
```

接收方先在字节流里找帧头，再读长度，再收齐数据，最后验证校验。校验对了才算一帧有效。

### 校验

| 算法 | 做法 | 能发现的错误 |
|---|---|---|
| sum8 | 所有字节相加取低 8 位 | 大部分单字节错误 |
| xor | 所有字节异或 | 奇数个比特翻转 |
| CRC-16/CRC-32 | 把数据看作多项式除以生成多项式取余数 | 突发错误，最常用 |

CRC 有很多变种：多项式、初值、是否反转、结果异或值都可能不同。例如 CRC-16/MODBUS 和 CRC-16/CCITT-FALSE 结果不同。写错一个参数，校验永远对不上。这是 AI 写协议代码时最常见的错误之一，所以设计上让 ICD 从一个**命名的算法表**里选，而不是让 AI 自己写 CRC。

### ICD

**ICD**（Interface Control Document，接口控制文档）是描述"一条消息里每个字段在哪、怎么解释"的文档，例如：

| 字段 | 偏移（字节） | 长度 | 字节序 | 类型 | 比例 | 单位 | 说明 |
|---|---|---|---|---|---|---|---|
| status | 4 | 1 | — | u8 位域 | — | — | bit0：自检通过 |
| voltage | 5 | 2 | 小端 | i16 | 0.01 | V | 测得电压 |
| temp | 7 | 2 | 小端 | i16 | 0.1 | °C | 温度 |

**字节序**：多字节整数先放低字节叫**小端**（x86 就是小端），先放高字节叫**大端**（网络协议常用）。0x1234 小端存为 `34 12`，大端存为 `12 34`。

**比例因子**：协议里常把 5.00 V 存成整数 500，乘以 0.01 才得到物理值。

**位域**：一个字节里每一位代表一个开关状态，需要按位取出。

**协议解码**就是按照 ICD 把原始字节翻译成有名字、有单位的字段值。本项目把 ICD 当作**数据**（一张字段表），由终端统一解码，而不是让每个测试写一段解析代码。详见设计文档第 6 章。

> 延伸阅读：Ross Williams "A Painless Guide to CRC Error Detection Algorithms"；CRC RevEng 的 CRC 目录（reveng.sourceforge.io/crc-catalogue）；Kaitai Struct 和 Python construct 库文档（两种用"声明"描述二进制格式的工具）；cantools 的 DBC 格式（CAN 的 ICD 标准格式）。

## 10. 进程、线程、锁和回调

| 概念 | 解释 | 本项目中的例子 |
|---|---|---|
| **进程** | 一个运行中的程序，有自己独立的内存 | 每个资源服务器是一个 Python 进程；终端有 Electron 主进程、渲染进程、Python 后端进程、OpenCode 进程 |
| **线程** | 进程内部并行执行的一条路径，共享进程内存 | 采样线程、串口读线程、厂商 SDK 的回调线程 |
| **锁（Lock）** | 保证同一时刻只有一个线程进入某段代码 | 环形缓冲的 `threading.Lock`；设备的 `io_lock` 保证同一时刻只有一个调用在操作驱动 |
| **竞态条件** | 两个线程同时改同一份数据，结果取决于谁先谁后 | 没有锁时，两个线程同时追加记录可能拿到同一个序号 |
| **回调线程** | SDK 自己创建的线程，数据到达时调用你注册的函数 | 1394 卡收到报文时在它的线程里调用适配器的函数 |
| **异步（async）** | 单线程里用 `await` 让等待 I/O 时去做别的事 | SDK 的 HTTP 服务、SSE 推送都是异步的 |

**规则**：在回调里只做最少的事，把数据放进线程安全的缓冲区就返回，不要在回调里做耗时操作或再调 SDK。本项目 SDK 的 `publish()`、`rx()`、`tx()` 都是线程安全的，可以直接在回调里调用。

> 延伸阅读：《操作系统导论》（OSTEP，免费在线）的"并发"部分；Python 文档 `threading`、`asyncio`。

## 11. 时间和时钟

计算机有两种时钟：

| 时钟 | 特点 | 用途 |
|---|---|---|
| **墙钟**（wall clock，`time.time()`） | 日历时间，可以被 NTP 或人手工调整，可能跳变甚至倒退 | 显示给人看、写日志 |
| **单调时钟**（monotonic，`time.perf_counter()`） | 只增不减，不受调整影响，但起点没有意义 | 测量间隔 |

本项目的做法：服务启动时读一次墙钟作为起点，之后都用"起点 + 单调时钟流逝量"。这样得到的时间是 Unix 毫秒，看起来像墙钟，但永远不会倒退（`clock.py` 的 `now_ms()`）。

### 两台电脑的时钟不一样

工控机 A 和测试终端的时钟可能差几十毫秒甚至几秒。要比较"A 上 12:00:00.100 发生的事"和"终端 12:00:00.150 发出的命令"，必须先估计两者的**时钟偏移**。

最简单的方法（Cristian 算法，NTP 的核心思想）：

```
终端                                 服务器
 t0 ──── GET /time ─────────────►
                                   读自己的时钟 = S
 t1 ◄─── {serverTime: S} ────────
偏移估计  offset ≈ S − (t0 + t1) / 2
不确定度  ± (t1 − t0) / 2          ← 往返时间越短越准
```

反复测几次，取往返时间最短的那次。局域网里往返通常在 1 ms 以内，所以对齐精度约为亚毫秒到几毫秒。这决定了本项目判定时间窗口的精度下限：**毫秒级**。需要微秒级时序的测量必须由仪器自己完成（例如示波器测上升时间），再把结果作为数值返回。

> 延伸阅读：维基百科 "Cristian's algorithm"、"Network Time Protocol"；RFC 5905（NTPv4）。

## 12. 网络和 HTTP

| 概念 | 解释 |
|---|---|
| **IP 地址** | 网络上一台电脑的地址，例如 `192.168.3.63` |
| **端口** | 一台电脑上区分不同服务的编号，例如 8011、8012；一个资源服务器占一个端口 |
| **TCP** | 可靠、有序的字节流连接，丢包自动重传 |
| **HTTP** | 基于 TCP 的"请求—响应"协议：客户端发一个请求（方法 + 路径 + 头 + 正文），服务器回一个响应（状态码 + 头 + 正文） |
| **URL** | `http://192.168.3.63:8011/streams/ai0?from=latest`：协议、主机、端口、路径、查询参数 |
| **JSON** | 文本数据格式：`{"v": 4.98, "t": 1790000000123.4}` |

常见状态码：

| 状态码 | 含义 |
|---|---|
| 200 | 成功 |
| 401 | 没带令牌或令牌错 |
| 404 | 路径不存在 |
| 500 | 服务器内部错误 |

```
请求:  GET /health HTTP/1.1
       Host: 192.168.3.63:8011

响应:  HTTP/1.1 200 OK
       Content-Type: application/json

       {"healthy": true, "serverId": "PCI1710L_MCP", "state": "open", "sdkVersion": "0.4.0"}
```

## 13. 长连接：SSE 和 WebSocket

普通 HTTP 是"问一次答一次"。要让服务器**持续**把新数据推给客户端，有三种办法：

| 方式 | 做法 | 缺点 |
|---|---|---|
| 轮询 | 客户端每 100 ms 问一次"有新数据吗" | 延迟高、浪费请求，两次询问之间的数据要靠序号补 |
| **SSE**（Server-Sent Events） | 一个 HTTP 响应永远不结束，服务器不断往里写事件 | 只能服务器 → 客户端单向 |
| **WebSocket** | 先用 HTTP 握手，然后升级成双向的消息通道 | 要自己设计续传、心跳等 |

SSE 的格式非常简单，就是纯文本，每个事件以空行结束：

```
event: hello
id: 7f3a:1024
data: {"streamId":"ai0","streamType":"scalar","epoch":"7f3a","fromSeq":1024,"serverTime":1790000000123.4}

event: batch
id: 7f3a:1027
data: {"records":[{"seq":1024,"t":1790000000125.0,"v":4.98},{"seq":1025,"t":1790000000225.0,"v":4.99},{"seq":1026,"t":1790000000325.1,"v":4.98}],"watermark":1790000000325.1}

```

SSE 自带**断点续传**：客户端断线重连时，把最后收到的 `id` 放在请求头 `Last-Event-ID` 里，服务器从那里接着发。浏览器的 `EventSource` 对象会自动做这件事。

本项目数据面只需要"服务器 → 终端"单向推送，所以选了 SSE。续传和按行解析都是现成的，用 `curl` 就能直接看到数据流，调试很方便。

> 延伸阅读：MDN "使用服务器发送事件"；WHATWG HTML 标准 "Server-sent events" 一节；RFC 6455（WebSocket）。

## 14. RPC、MCP 和 AI Agent

### RPC

**RPC**（Remote Procedure Call，远程过程调用）就是"像调本地函数一样调远程电脑上的函数"。**JSON-RPC 2.0** 是一种简单的 RPC 格式：

```json
请求  {"jsonrpc": "2.0", "id": 7, "method": "tools/call", "params": {...}}
响应  {"jsonrpc": "2.0", "id": 7, "result": {...}}
```

### MCP

**MCP**（Model Context Protocol，模型上下文协议）是 Anthropic 在 2024 年发布的开放协议，建立在 JSON-RPC 2.0 之上，规定了 AI 应用怎么发现和调用外部"工具"。本项目用到的核心方法：

| 方法 | 作用 |
|---|---|
| `initialize` | 建立会话，交换版本和能力 |
| `tools/list` | 列出服务器提供的所有工具：名字、描述、输入参数的 JSON Schema、输出的 JSON Schema |
| `tools/call` | 调用一个工具：`{name, arguments, _meta}` |

**传输方式**有两种：

- **stdio**：本地子进程，通过标准输入/输出通信；
- **Streamable HTTP**：通过 HTTP POST 通信，本项目的资源服务器用的就是这种，路径 `/mcp`。

### `_meta` 是什么

MCP 规范给请求的 `params` 和响应的 `result` 都保留了一个叫 `_meta` 的字段，用来放**不属于业务参数、但协议两端需要的附加信息**。这样工具的业务参数（`arguments`）保持干净，AI 看到的工具参数表里也不会出现这些"管道"字段。

本项目的 `tools/call` 请求：

```json
{
  "method": "tools/call",
  "params": {
    "name": "pci6208v_set_voltage",
    "arguments": {"hardwareId": "PC1_MCP.PCI6208V_CARD_0", "channel": 1, "voltage": 2.5},
    "_meta": {"operationId": "run42-step7-op1", "leaseId": "lease-9c1e4f..."}
  }
}
```

- `operationId`：测试引擎给这次调用起的编号。服务器把它贴到这次调用期间产生的所有流记录上（记录里的 `op` 字段），这样终端能把"这条串口数据"和"这次命令"关联起来。
- `leaseId`：证明调用者持有这台设备的租约（第 17 章）。

响应里的业务结果放在结构化结果中，是一个"信封"：

```json
{"ok": true, "data": {"channel": 1, "voltage": 2.5},
 "meta": {"operationId": "run42-step7-op1",
          "timing": {"start": 1790000000100.2, "end": 1790000000101.9},
          "streamRefs": [{"streamId": "ao1", "fromSeq": 88, "toSeq": 88}]}}
```

注意区分两个名字相近的东西：

- 请求里的 `_meta`：MCP 协议层的附加字段，放调用方提供的信息；
- 响应信封里的 `meta`：本项目自己的结果契约，放服务器返回的时间和证据位置。

### AI Agent

**LLM**（大语言模型）本身只会生成文字。**Agent** 是一个循环：

```
模型读到任务和可用工具列表
  → 输出"我要调用工具 X，参数是 …"
  → 程序真的去调用，把结果文字返回给模型
  → 模型再决定下一步
  → … 直到完成
```

**工具描述写得好不好**直接决定 Agent 用得对不对。所以 SDK 要求每个工具描述至少 80 个字，说清"它证明什么、不证明什么、失败后怎么办"。本地部署的小模型能力有限，工具太多会选错，所以设计上按任务阶段只给它一部分工具（设计文档第 8 章）。

本项目用 **OpenCode**（开源的编程 Agent）作为 Agent 外壳，接本地的 OpenAI 兼容模型服务。终端后端作为一个 MCP 服务器，给它提供平台工具（建计划、校验计划、运行、看结果……）。

> 延伸阅读：MCP 官方规范 modelcontextprotocol.io（"Basic → _meta"、"Server → Tools"、"Transports"）；JSON-RPC 2.0 规范；OpenCode 文档；Anthropic 文章 "Building effective agents"。

## 15. 数据流：缓冲、环形缓冲、序号和水位线

### 为什么要缓冲

采集卡每 10 ms 产生一个值，终端可能正在忙，网络可能卡一下。**缓冲区**就是生产者和消费者之间的一个仓库：生产者往里放，消费者按自己的节奏取。

### 环形缓冲（Ring Buffer）

固定大小的数组，写到末尾就绕回开头，覆盖最老的数据：

```
容量 8，已经写了 11 条（seq 0..10），最老的 0、1、2 已被覆盖

 下标:   0    1    2    3    4    5    6    7
       ┌────┬────┬────┬────┬────┬────┬────┬────┐
       │ s8 │ s9 │s10 │ s3 │ s4 │ s5 │ s6 │ s7 │
       └────┴────┴────┴────┴────┴────┴────┴────┘
                      ▲写指针   ▲最老（tail = 3）
       最新 head = 11（下一条的序号）
```

优点是内存固定、不会无限增长，写入极快。代价是**消费者太慢时最老的数据会丢**，所以必须能告诉消费者"你丢了哪些"。

### 序号（seq）和纪元（epoch）

- 每条记录有一个**单调递增的序号** `seq`。消费者记住"我读到了 1024"，下次从 1025 接着要。这叫**游标**。Kafka 里叫 offset。
- 服务重启后序号从 0 重新开始，旧游标就失效了。所以再加一个 **epoch**（每次启动随机生成的纪元号）。游标写成 `epoch:seq`，epoch 对不上就知道服务重启过。

### 缺口（gap）

消费者要的 seq 已经被覆盖了，服务器发一个 `gap` 事件说明"1000～1023 丢了，原因是 overflow"。判定时，如果要用的时间窗口里有缺口，就不能判 Pass 或 Fail，只能判 **Inconclusive**（证据不足）。

### 水位线（watermark）

这是最容易被忽略、但对判定最关键的概念。

假设你要判断"命令发出后 200 ms 内，串口没有收到 ERROR"。你在第 150 ms 时还没看到 ERROR，能说"没有 ERROR"吗？**不能**，数据可能还在路上。

**水位线**是服务器的一个承诺：**"时间 ≤ watermark 的记录我已经全部发给你了"**。只有当 watermark 越过窗口末尾（命令时刻 + 200 ms），"窗口内没有 ERROR"才是确定的结论。所以服务器即使没有新数据，也会定期发 `status` 事件推进水位线；否则终端要等很久才能下结论。

### 按需采样

对"要主动读才有数据"的设备（例如每次调用 `GetValue` 读一个电压），没人订阅时不必一直读。SDK 的 `Sampler` 只在有订阅者时才以固定频率轮询设备，这叫**按需（demand-driven）**。

### 电平型和事件型

- **电平型**（scalar、bits）：一条记录的值一直有效，直到下一条出现。例如 DI 状态 3 小时没变，也只有一条记录。新订阅者需要拿到"当前仍然有效的那一条"，所以 `since` 参数对电平型流会从"那一刻有效的记录"开始。
- **事件型**（bytes、frames）：每条记录是一个独立事件，过去了就过去了。

> 延伸阅读：维基百科 "Circular buffer"；LMAX Disruptor 技术论文；Kafka 文档 "Introduction"（offset、consumer 概念）；Tyler Akidau "Streaming 101/102"（O'Reilly，watermark 概念的经典解释）。

## 16. 请求/响应、发布/订阅、控制面和数据面

| 模式 | 特点 | 适合 |
|---|---|---|
| **请求/响应** | 问一次答一次，调用方知道结果对应哪个请求 | 发命令、改设置、查询配置 |
| **发布/订阅** | 生产者只管发布，订阅者各自接收，双方互不知道 | 连续的测量数据、日志 |

**控制面**和**数据面**是网络设备里的说法：

- **控制面**决定"做什么"。量小、要求可靠、每个动作都要确认，适合请求/响应。本项目用 **MCP 工具调用**。
- **数据面**负责"搬数据"。量大、连续、要能续传，适合发布/订阅。本项目用 **SSE 流**。

分开的好处：

- 控制命令不会被大量数据堵住；
- 数据可以被多个订阅者（测试引擎、运行台示波器、录制器）同时使用；
- 一个动作产生的证据可以通过 `operationId` 和 `streamRefs` 精确关联起来。

HardwareHarness 还有第三类接口：**声明**。它回答"这台设备是什么、长什么样、有哪些端口和流"。声明很少变化，用普通的 HTTP GET 读取即可（`/device`、`/assets/...`）。

> 延伸阅读：维基百科 "Publish–subscribe pattern"、"Control plane"；Martin Kleppmann《数据密集型应用系统设计》（DDIA）第 11 章"流处理"。

## 17. 可靠性：超时、幂等、租约和安全状态

### 超时不等于没执行

你让电源"打开输出"，3 秒没收到回复。电源到底开了没有？**不知道**。可能：

- 命令没送到；
- 命令执行了，但回复丢了；
- 命令还在执行。

所以本项目的铁律是：**物理动作的结果未知时，绝不自动重发**。先去查状态或证据，确认之后再决定。在测试引擎里，这类调用进入"待核销"列表，由人或 AI 通过 `reconcile_test_operation` 确认实际结果。

### 幂等

**幂等**指做一次和做多次效果相同。例如"设电压为 5 V"是幂等的，"电压加 1 V"不是，"发一帧报文"也不是（对方会收到两帧）。工具的 `kind` 标注了这一点：`actuate` 类工具的 `retry` 是 `never_after_dispatch`。

### operationId

给每个动作一个唯一编号，所有相关记录都带上它，事后能准确追溯"这条数据是哪个动作引起的"。这是分布式系统中关联请求的通用做法（类似分布式追踪里的 trace id）。

### 租约（Lease）

多个终端可能同时连着同一台设备。如果两个人同时控制一个电源，会很危险。**租约**就是"排他使用权"：

- 拿到租约的人才能执行 `configure`、`actuate` 类工具；
- 其他人只能读（`read`），或者执行 `safe`（回安全态）。

一个关键问题是：**持有者突然死机了怎么办？** 租约永远不释放，设备就永远被锁住了。所以租约要靠**心跳**维持：

- 持有者每隔 2 秒告诉服务器"我还活着"；
- 服务器超过 10 秒没收到心跳，就认为持有者没了，自动释放租约，并把设备置于安全状态。

本项目的租约**没有业务时限**：只要终端开着、心跳在发，就一直占有。终端关闭，心跳停止，租约自动取消（设计文档第 4.5 节）。

租约这个概念来自 1989 年 Gray 和 Cheriton 的经典论文，今天的 etcd、ZooKeeper、Kubernetes 的 Lease 对象都是同一个思想。

### 安全状态和看门狗

- **安全状态（safe state）**：所有输出回到无害值（电压 0 V、继电器断开、电源关闭）。服务启动后、停止前、租约丢失时都会进入安全状态。
- **看门狗（watchdog）**：定期检查设备是否还在。打不开就按 5 s、10 s、30 s 的间隔重试。
- **状态机**：设备有明确的状态（`initializing → open → closing → closed`，出错为 `unreachable`、`faulted`）。只有 `open` 时才接受操作。

> 延伸阅读：Gray & Cheriton 1989 "Leases: An Efficient Fault-Tolerant Mechanism for Distributed File Cache Consistency"；Stripe 博客 "Designing robust and predictable APIs with idempotency"；Martin Kleppmann "How to do distributed locking"；Kubernetes 文档 "Leases"。

# 第三部分 测试工程

## 19. 测试计划、步骤和表达式

**测试计划**是一棵步骤树。步骤分两类：

| 类别 | 步骤 | 作用 |
|---|---|---|
| **动作和判定** | InvokeTool | 调用一个设备工具（设电压、发一帧、切继电器），可以断言它的返回值 |
| | Observe | 在一个时间窗口里观察一条流，计算统计量并断言，例如"命令后 100～600 ms 内 ai3 的平均值在 4.9～5.1" |
| | Expect | 等待一个事件，例如"命令后 500 ms 内串口收到 `OK`"，得到命中时刻和延迟 |
| | Guard | 包住一组步骤，全程守护一个条件，例如"整个过程电流不超过 2 A"，违反就中止或判失败 |
| | ManualCheck | 让操作员判定（看画面、听声音），记录结论和备注 |
| **流程控制** | Sequence / Group | 顺序执行 |
| | If | 条件分支 |
| | Repeat / ForEach | 重复、遍历一组测点或工位 |
| | Parallel | 并行执行 |
| | Retry | 失败后重试 |
| | SetVariable / Evaluate | 计算并保存中间值 |
| | Delay | 等待 |
| | PublishResult | 输出结果 |

**表达式**用来写条件和计算，例如 `steps.readV.value * steps.readI.value < parameters.maxPower`。本项目的表达式语言是 CEL（Google 的 Common Expression Language）的一个安全子集：

- 只能读数据、做运算；
- 不能访问文件，不能调用任意代码；
- 所以 AI 写错也不会造成危险。

**参数**是计划的输入（例如额定电压），**变量**是运行中产生的中间值（例如上一步读到的电压）。

> 延伸阅读：CEL 官方网站 cel.dev；Google OpenHTF 项目（开源的硬件测试框架，phase/measurement 概念可参考）；NI TestStand 文档中的 "Sequence" 概念。

## 20. 判定、证据和时间窗口

### "读最新值"为什么不够

传统做法是"设电压 → sleep 500 ms → 读一次 → 比较"。问题在于：

1. 读到的这个值是什么时候采的？可能是设电压之前的旧值。
2. 只读一个点，碰上噪声就误判。
3. 事后无法复查：当时到底读到了什么、前后是什么样的？

### 本项目的做法：以动作为锚点的时间窗口

```
        动作 InvokeTool 完成（锚点 = 服务端 timing.end）
              │
  ────────────┼────────[=====窗口=====]──────────► 时间
              0      +100 ms        +600 ms
                      在这段时间里，ai3 的所有采样点：
                      mean = 4.99, min = 4.97, max = 5.01, count = 50
                      断言 4.9 ≤ mean ≤ 5.1  →  Pass
```

- **锚点**用服务端时钟，与流记录用的是同一个时钟，没有对时误差。
- 窗口内所有样本都参与计算，还规定最少样本数。
- 窗口数据和判定结果一起保存，事后可以重新判定。

### 三种结果

| 结果 | 含义 |
|---|---|
| **Pass** | 证据充分，满足条件 |
| **Fail** | 证据充分，不满足条件 |
| **Inconclusive** | 证据不足，无法判断，并给出原因：窗口有缺口（gap）、水位线没到（watermark_timeout）、样本太少（insufficient_evidence）、对时误差大于窗口精度（clock_uncertainty） |

区分 Fail 和 Inconclusive 非常重要：前者说明产品有问题，后者说明测试系统本身有问题（线断了、服务挂了），处理方式完全不同。

## 21. 独立测量和协议回报

| 证据来源 | 例子 | 可信度 |
|---|---|---|
| **独立测量** | 采集卡直接测 DUT 输出口电压 | 高：测量链路和 DUT 无关，可以追溯到仪器和通道 |
| **仪器自测** | 电源自己报告的输出电压 `MEAS:VOLT?` | 较高：是仪器的测量，但测的是仪器端口，不是 DUT 端 |
| **协议回报** | DUT 通过 1394 报文说"我测到 5.00 V" | 取决于 DUT：它测错了也会报"正确" |

资料中大量测试项（尤其 D 项目）的证据是协议回报：台架给 DUT 施加一个已知激励（例如 THC032A 输出 3.000 V），DUT 把自己测到的值通过 1394 报回来，台架比较两者。这是测试 **DUT 的采集功能**，而不是测 DUT 的输出。要判定这类测试，必须先把报文解码成字段（第 9 章 ICD），这正是设计里"被测产品协议层"要解决的问题。

## 25. 常见问题

**问：为什么不把判定放在资源服务器上？**
答：一个判定常常跨多台设备（6208V 输出、1710L 测量），只有终端同时看得到所有设备的数据。判定集中在一处，调试和正式运行才用同一套逻辑；原始数据保存下来，还能事后重新判定。

**问：为什么每台设备一个服务进程？**
答：隔离。一张卡的驱动崩溃不影响别的卡；每个服务可以单独部署、升级、重启。代价是进程多一些，对工控机来说完全可以接受。

**问：数据面为什么不用 MQTT、Kafka 这类消息中间件？**
答：数据只有一个生产者（设备服务），消费者只有终端，拓扑很简单。中间件要额外部署和维护一个组件。每个服务内置一个环形缓冲加 SSE 就够了，续传和缺口检测也都有了。

**问：被测产品的协议为什么不在资源服务器里解码？**
答：资源服务器描述的是"测试资源"（一张 1394 卡），它不应该知道插在另一头的是哪个产品。换一个产品，只需要换终端里的 ICD，不需要重新部署服务器。

**问：AI 在这套系统里做什么，不做什么？**
答：
- **AI 做**：
  - 照着厂商 SDK 写适配器，并在模拟器上自测；
  - 照着 DUT 手册写 ICD；
  - 编写和校验测试计划；
  - 调试和分析结果。
- **AI 不做**：
  - 绕过安全范围检查；
  - 自动重发结果未知的物理动作；
  - 在没有实物冒烟测试的情况下宣布适配完成。

**问：为什么界面、Agent、命令行要由同一个“操作注册表”生成？**
答：同一个动作（例如“开始运行”）如果在 HTTP 接口、Agent 工具、命令行里各写一遍，权限检查、审计和“结果未知不重试”这些规则就要写三遍，迟早会有一处漏掉。只定义一次，其余自动生成，三种入口就走同一条检查路径；前端的 TS 类型也从同一份定义生成，前后端不会对不上。这和 gRPC、OpenAPI 的“契约优先”是同一个思路（见参考资料）。

**问：为什么把运行日志作为唯一记录？**
答：恢复、核销、出报告、重新判定，需要的都是“按顺序发生过什么”。如果另外再存一份可变的“当前状态”，两者迟早会不一致。只追加写日志、其余都从日志推导，就是事件溯源（Event Sourcing）的做法。
