# v4 工程转换与旧体系退役

本次开发未打开或转换用户现有工程，也未改动设备登记资料、`mcp_servers` 或当前 STM32
示例工程。转换验证全部使用临时目录，包含中文和空格路径。

## 转换结果

首次打开 v1–v3 清单时，转换器只提取工程身份、名称、接线和时间信息，写入 v4，移除
`task`。不解释节点任务，不把节点转换为 Python，也不恢复旧节点执行栈。有效 v4 工程
打开时保持原清单字节不变。未来版本和非法清单拒绝打开。

原始清单与 `.hardwareharness/logs/runs` 中的旧运行文件保存到
`.hardwareharness/backups/legacy-<原清单 SHA256 前 24 位>`。先在 `.pending` 目录复制，
逐文件核对 SHA256、flush/fsync 后写入 `conversion.json` 阶段记录，再提交备份目录。
原日志目录移入备份的 `retired-runs`；独立的 `runs` 副本继续作为已验证原始证据。
之后才原子更新工程清单。

转换器拒绝符号链接与 Windows reparse point。提交前再次核对当前清单字节；期间发生
外部编辑则保留编辑并中止转换。备份损坏、日志变化、不完整状态或原子提交失败均报错，
不会用新的副本覆盖已封存的备份。封存后、目录提交前崩溃可以继续同一事务。

新 Run 使用 `.hardwareharness/logs/application-runs`，附件使用独立目录。旧 Run 只保留
原始备份，不进入新日志界面。新进程未正常结束时，重启读取后标记为中断，不自动重试。

## 回归证据

`python/tests/projects/test_v4_conversion.py` 覆盖三个旧版本、原始字节、保留字段、节点
任务不解析、提交失败重试、备份损坏、无旧日志、v4 字节保留、封存阶段恢复、日志被修改、
不完整备份、链接拒绝和转换期间外部清单修改。

删除的旧节点引擎、契约、编辑器、检查点及旧 Run 读取器均记录原始 Git revision、路径
与 SHA256，见本目录 retirement 清单。共享的取消和时间工具迁到 `compat`，设备、接线、
占用及旧全局存储升级仍执行保留规格检查。
